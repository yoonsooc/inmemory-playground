# device-registry PRD

작성일: 2026-09-30
상태: 진행 중 (1단계 SSE 구현 전, 설계 재검토 완료)

이 문서는 "무엇을 왜 만드는가"를 적는다. "어떻게 만들기로 했고 왜 그렇게 정했는가"는 `adr/`에 결정 단위로 적는다.
구현 체크리스트가 바뀌면 여기를 고치고, 바뀐 이유는 ADR로 남긴다. (CLAUDE.md는 git으로 추적하지 않으므로 여기가 이력의 원본이다.)

## 1. 배경

두 질문.

1. 디바이스(테이블오더 기기)의 연결 정보를 서버 메모리에 들고 있는데, 서버를 증설하면 어떻게 되는가?
2. 락을 실무에서 어떻게 적용했는가?

당시 "Redis를 써 본 적 없다"고 답했다. 이 프로젝트는 그 질문에 대한 답을 동작하는 코드와 실험 로그로 만든다.
가치는 코드 양이 아니라 "왜 이렇게 설계했는가"를 설명할 수 있는 상태에 있다. 그래서 로직은 직접 작성하고, 설계 결정마다 ADR을 남긴다.

## 2. 문제 정의

기기는 서버가 먼저 말을 걸어야 하는 순간이 있다. 주문 상태 변화, 품절 반영, 카운터의 결제 요청, 원격 잠금 같은 것이다.
이를 위해 기기는 서버와 오래 유지되는 연결(SSE)을 맺는다. 이 연결은 특정 서버 프로세스 한 곳에만 존재한다.

서버가 한 대일 때는 문제가 없다. 서버가 여러 대가 되면 다음이 깨진다.

- 운영자가 "지금 어떤 기기가 온라인인가"를 물으면 서버마다 다른 답을 한다. 각자 자기 연결만 알기 때문이다.
- "7번 기기에 결제 요청을 띄워라"는 명령이 7번의 연결을 쥐지 않은 서버에 도착하면 전달할 수 없다.
- 서버 한 대가 죽으면 그 서버가 알던 연결 정보가 함께 사라지고, 다른 서버는 그 사실을 모른다.

핵심 관찰: 연결은 서버를 "상태 있는 존재"로 만든다. 일반 REST 서버의 "어느 서버가 받아도 된다"는 전제가 연결에는 성립하지 않는다.

## 3. 목표와 비목표

### 목표

- 서버가 몇 대든 "어느 기기가 어느 서버에 연결되어 있는가"를 모든 서버가 같은 답으로 알 수 있다.
- 명령을 아무 서버에 보내도 연결을 쥔 서버가 기기에 전달한다.
- 서버가 죽으면 그 서버의 연결 기록이 사람 개입 없이 정리된다.
- 서버를 추가할 때 기존 서버, 기기, 설정을 건드리지 않는다.
- 위 네 가지를 실험 로그로 증명한다.

### 비목표 (구현하지 않는다)

인증, UI, 웹소켓 병행 구현, K8s 배포, 명령 전달 보장(at-least-once 등), 라이브러리화.

## 4. 행위자

| 행위자 | 역할 | 서버에 보내는 것 |
|---|---|---|
| 기기 (시뮬레이터 스크립트) | SSE 연결을 열고 유지한다. 끊기면 재연결한다 | `GET /devices/{id}/events` (오래 열림) |
| 운영자 (curl) | 상태를 조회하고 명령을 내린다 | `GET /devices`, `GET /devices/{id}`, `POST /devices/{id}/command` |
| 앱 서버 (Spring Boot, 2대 이상) | 연결을 쥐고, 공유 기록을 쓰고, 명령을 라우팅한다 | Valkey 읽기·쓰기, Pub/Sub |
| nginx | 라운드로빈. 기기와 운영자는 이 주소만 안다 | |
| Valkey 클러스터 (master 3 + replica 3) | 서버 간 공유 상태의 유일한 저장소 | |

## 5. 구조

```
                          ┌──────────────────────── 서버 로컬 상태 ─────────────────────────┐
 [기기 dev-1]             │   ┌── app-1 (8081) ─────────────┐                              │
   │ GET /devices/dev-1/events (SSE, 오래 열림)              │                              │
   ├─────────────────▶ nginx ──▶│ Map<deviceId, SseEmitter>   │──┐                           │
   │                   (8080)   │   dev-1 → emitter           │  │ 등록·임대 갱신·해제        │
   │                   round-   └─────────────────────────────┘  │ (server_id 를 쓰는 유일한 경로)
   │                   robin                                     ▼                           │
   │                        │   ┌── app-2 (8082) ─────────────┐   ┌──── Valkey cluster ────────┐
   │                        └──▶│ Map<deviceId, SseEmitter>   │──▶│ device:dev-1  HASH (TTL)   │
   │                            │   (비어 있음)               │   │   server_id = app-1        │
   │                            └─────────────────────────────┘   │   status, last_seen        │
   │                                   ▲                          │ devices:known SET          │
 [운영자 curl]                         │                          └────────────────────────────┘
   │ GET /devices        (아무 서버에나. Valkey 만 읽으므로 답이 같다)
   ├───────────────────▶ nginx ────────┘
   │ POST /devices/dev-1/command   (받은 서버 ≠ 연결 주인일 수 있음)
   └───────────────────▶ nginx ──▶ app-2 ──▶ Valkey Pub/Sub ──▶ app-1 ──▶ emitter ──▶ dev-1
```

| 상태 | 위치 | 원본/파생 |
|---|---|---|
| 실제 TCP 연결 | 각 서버의 `Map<deviceId, SseEmitter>` | 원본. 그 서버만 안다 |
| "어느 서버가 어느 기기를 쥐고 있는가" | Valkey `device:{id}` 해시 (TTL) | 파생. 원본을 다른 서버에게 알리기 위한 기록 |

## 6. 기능 요구사항 (구현 체크리스트)

체크리스트는 CLAUDE.md의 원안을 옮긴 것이고, 변경된 항목은 ADR 번호를 달았다.

| # | 항목 | 상태 | 관련 ADR |
|---|---|---|---|
| 1 | 기기 시뮬레이터가 SSE로 연결한다. **서버가** 주기적으로 ping을 보내고 기기는 수신을 로그로 확인한다 | 미구현 | ADR-0002, ADR-0003 (원안 "기기가 하트비트 전송"에서 변경) |
| 2 | 연결을 쥔 서버가 Valkey에 `device:{id}` 해시(server_id, status, last_seen)를 쓰고 TTL로 자동 만료한다. TTL 갱신도 그 서버가 한다 | 해시 저장은 구현됨. 갱신 주체 변경 미반영 | ADR-0001, ADR-0003 |
| 3 | 전체 기기 상태 조회 API. 어느 서버에 호출해도 같은 결과 | 구현됨 | ADR-0001 |
| 4 | 임의 서버로 명령 POST → Pub/Sub → 연결을 쥔 서버가 SSE로 기기에 전달 | 미구현 | ADR-0005 (제안) |
| 5 | 서버 한 대 kill 실험: 재연결과 상태 자동 만료를 로그로 확인 | 미구현 | |
| 6 | (선택) 낙관적 락으로 동시 상태 변경 데모 | 미정 | |

연결 해제 시 기록 정리 규칙은 ADR-0004에 있다. 체크리스트에는 없지만 2번과 5번이 올바르게 동작하기 위한 전제다.

## 7. 비기능 요구사항

- 서버 로컬 상태는 emitter 맵 하나로 제한한다. 그 외의 모든 상태는 Valkey에 둔다.
- 공유 기록은 연결 주인만 쓴다. (ADR-0003)
- "확인하고 나서 실행"이 필요한 곳은 두 명령 사이의 간격을 없앤다. (ADR-0004)
- VPN 경유를 허용한다. 기능 검증이 목적이므로 지연은 무관하다.

## 8. 실험 계획 (완성 기준의 일부)

각 실험은 시각이 찍힌 로그와 함께 README에 들어간다.

1. 기기가 app-1에 연결된 상태에서 app-2에 전체 조회 → 같은 결과
2. app-1 kill -9 → TTL 경과 후 app-2 조회에서 OFFLINE, 기기 시뮬레이터의 재연결 로그, 재연결이 app-2에 착지
3. 기기 시뮬레이터 kill -9 → 서버의 ping 실패 로그, 기록 즉시 정리
4. 명령을 연결 주인이 아닌 서버에 POST → Pub/Sub를 거쳐 기기가 수신
5. app-1 재기동 → 기기가 자동 재연결하고 ONLINE으로 복귀

2026-09-11에 1, 2(착지 제외), 3, 5를 초안 코드로 한 번 확인했다. 초안은 되돌렸고, 직접 재구현한 뒤 다시 측정한다.

## 9. 완성 기준

- README: 구조 그림 + 위 실험 로그
- 블로그 글 1편. 서사는 "흔한 존재 확인 패턴으로 시작했고, 연결이 들어오자 기록의 뜻이 바뀌었고, 그래서 쓰는 주체를 옮겼다" (ADR-0003)
- 타임박스 2~3일. 넘기면 스코프를 잘라 글부터 쓴다.

## 10. 알려진 한계 (README에 그대로 옮긴다)

- 서버가 죽은 뒤 TTL이 지날 때까지 기록이 ONLINE으로 남는다. TTL을 줄이면 창은 좁아지고 갱신 부하는 늘어난다.
- 조용히 죽은 기기(네트워크 단절)는 TCP 쓰기 실패가 날 때까지 감지가 늦다. 같은 호스트에서 kill -9 한 실험은 현실보다 유리한 조건이다.
- 서버 한 대 재배포 시 그 서버의 연결이 동시에 끊겨 재연결 폭주가 난다. 재연결 지연에 무작위성을 주는 것이 관행이나 이 프로젝트에서는 구현하지 않는다.
- `devices:known` SET은 무한히 자란다.

## 11. 백로그 (완성 기준 밖)

- 클라이언트 → 서버 보조 하트비트로 `last_seen`만 갱신 (기기 생존 감지 지연이 문제가 될 때)
- 연결 토큰을 해시에 저장해 같은 서버 재연결 경합을 저장소 수준에서 구분
- 재연결 지연 지터
- 명령 전달 확인(ack)

## 12. 용어

- **임대(lease)**: 유효 기간이 있는 기록. 주기적으로 연장하지 않으면 저절로 사라진다. 여기서는 TTL이 걸린 `device:{id}` 해시.
- **연결 주인**: 해당 기기의 SSE 연결을 실제로 쥐고 있는 서버 프로세스.
- **반쯤 열린 연결**: 한쪽은 살아 있다고 믿지만 상대는 이미 사라진 TCP 연결. 종료 신호 없이 프로세스가 죽거나 네트워크가 끊길 때 생긴다.
- **원자적**: 여러 명령이 중간에 다른 명령이 끼어들 수 없이 한 번에 실행되는 것. Valkey에서는 Lua 스크립트 또는 MULTI/EXEC.
