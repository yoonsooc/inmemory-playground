# 0006. Valkey에 쓸 때 연결 번호(epoch)를 비교한다

상태: 채택 (구현하고 검증함, 2026-10-02)
날짜: 2026-10-01
보완 대상: ADR-0003 (전제에 숨은 조건이 있었다), ADR-0004 (삭제 조건이 server_id에서 epoch으로 바뀐다)
출처: 실험 기록 `experiments/2026-10-01-stage1-verification.md` "발견", backlog 0008

용어: 이 문서에서 **epoch**은 "그 연결이 맺어진 시각을 숫자로 적은 것"이다. 나중에 맺어진 연결일수록 숫자가 크다. **좀비 연결**은 실제로는 끊겼는데 서버가 아직 그 사실을 모르는 연결이다.

## 맥락

ADR-0003은 "연결을 쥔 서버가 갱신하면 틀린 기록이 생기지 않는다"고 했다. 여기에는 "서버는 자기 연결이 끊긴 것을 바로 안다"는 조건이 숨어 있었다. TCP는 그것을 보장하지 않는다. `write()`가 성공했다는 것은 커널 버퍼에 넣었다는 뜻일 뿐이라, 끊긴 연결에 보낸 ping도 한두 번은 성공으로 돌아온다. 기기의 프로그램만 죽은 경우에는 기기 쪽 운영체제가 "그런 연결은 없다"는 거절 응답(RST)을 돌려줘서 그 다음 쓰기부터 실패한다. 기기 전원이 꺼지거나 네트워크가 끊겨 응답해 줄 쪽이 없으면 수 분 동안 계속 성공한다.

실험에서 본 것:

```
02:59:10  옛 시뮬레이터 kill -9 (옛 dev-3 연결은 app-2에 있었음)
02:59:13  새 dev-3가 app-1에 연결. server_id=app-1
02:59:21  app-2가 끊긴 연결에 보낸 ping이 "성공" → 갱신이 server_id를 app-2로 덮어씀
02:59:29  app-1의 갱신이 다시 app-1로
02:59:32  app-2가 끊김을 알아챔. 삭제는 server_id가 app-1이라 건너뜀
```

8초 동안 기록은 app-2를 가리키는데 실제 연결은 app-1에 있었다. 4단계에서 명령은 `server_id`를 보고 보낼 서버를 정하므로, 이 사이에 온 명령은 사라진다. 또 app-2가 자기 갱신 직후에 끊김을 알아챘다면 "server_id가 나면 삭제"가 참이 되어 멀쩡한 연결의 기록을 지웠을 것이다.

## 결정

연결마다 epoch을 붙이고, Valkey에 쓰거나 지울 때마다 epoch을 비교한다. 원칙은 "먼저 쓴 쪽이 아니라 **나중에 연결된 쪽**이 이긴다"이다.

1. **epoch은 서버가 직접 만든다.** 연결 요청을 받은 순간 서버가 자기 시계(`System.currentTimeMillis()`)로 epoch을 정하고, emitter와 함께 맵에 넣는다. Valkey의 응답을 기다리지 않으므로 이 시점에 서버 쪽 정보는 다 채워진다.
2. **Valkey의 해시에도 `epoch` 필드를 둔다.** "지금 주인으로 인정된 연결의 번호"다. 서버가 맵에 들고 있는 값은 "내 연결의 번호"다. 이 둘을 비교한다.
3. **Valkey에 쓰는 동작은 한 종류다.** 서버가 자기 epoch을 인자로 넘기고, 스크립트가 판단한다.
   - 키가 없거나, 저장된 epoch이 내 것보다 작거나 같다 → 쓴다 (server_id, status, last_seen, epoch, TTL).
   - 저장된 epoch이 내 것보다 크다 → **쓰지 않고 0을 돌려준다.** 나보다 나중에 맺어진 연결이 있다는 뜻이다.
   - 연결 직후의 등록과 ping 때의 갱신은 같은 동작이다. 등록은 "첫 갱신을 ping 주기보다 먼저 한 번 하는 것"일 뿐이다. 실패하면 다음 ping에서 같은 쓰기를 다시 한다.
4. **0을 받은 서버는 자기 emitter를 닫는다.** 디바이스가 이미 버린 연결이므로 닫아도 디바이스가 다시 연결할 일이 없다. TCP가 알려 주기 전에 좀비를 정리하는 효과도 있다.
5. **삭제는 저장된 epoch이 내 것과 같을 때만 한다.** ADR-0004의 `server_id` 비교를 대신한다. 같은 서버로 다시 연결한 경우도 epoch이 다르므로 Valkey 안에서 구분된다(backlog 0005가 여기에 포함됨).

`server_id`는 계속 적는다. 4단계에서 명령을 어느 서버로 보낼지 정할 때 읽는 값이다. epoch은 "누가 쓸 자격이 있는가"만 가린다.

## 근거

- 연결을 만드는 쪽은 디바이스뿐이고, 디바이스는 새로 연결할 때 옛 연결을 버린다. 그래서 **가장 나중에 맺어진 연결이 진짜**다. epoch 비교는 이 판단을 Valkey가 직접 하게 만든다.
- 0(거부)의 뜻이 분명하다. "나보다 나중 연결이 있다"이므로 거부당한 쪽은 언제나 낡은 쪽이다.
- 락 실무 질문과 같은 구조다. 분산 락에서, 만료된 락을 들고 뒤늦게 쓰려는 클라이언트를 막으려고 쓰기마다 번호를 비교하는 장치(펜싱 토큰)와 같다.
- epoch을 서버가 직접 만들면 "맵에는 있는데 아직 덜 채워진 연결"이라는 상태가 생기지 않는다. 서버가 기억하는 것과 Valkey에 적힌 것을 한 번에 같이 바꿀 방법은 없으므로, 서버 쪽 정보가 Valkey의 응답에 기대지 않게 하는 것이 중요하다.

## 검토하고 고르지 않은 방법

### A. `server_id`가 다르면 거부 (가장 작은 구현)

갱신 스크립트가 "`server_id`가 나이거나 키가 없을 때만" 쓰고, 다른 서버면 0을 돌려준다. 0을 받은 서버는 자기 연결을 닫는다.

고르지 않은 이유: `server_id`가 다르다는 것만으로는 상대가 좀비인지 진짜인지 알 수 없어서, **먼저 쓴 쪽이 이긴다.** 키가 만료된 뒤 좀비가 먼저 다시 쓰면 진짜 연결이 거부당해 스스로 닫힌다.

좀비 = 서버 A의 옛 연결(epoch 100), 진짜 = 서버 B의 새 연결(epoch 200), 키는 만료되어 없는 상태에서:

| 순서 | A 방식 (server_id 비교) | 이 결정 (epoch 비교) |
|---|---|---|
| 1. 좀비가 먼저 갱신 | 키가 없으니 씀. `server_id=A` | 키가 없으니 씀. `server_id=A, epoch=100` |
| 2. 진짜가 갱신 | `server_id`가 A라서 **거부. 진짜 연결을 닫음** | 200 > 100 이라 **씀. `server_id=B, epoch=200`** |
| 3. 좀비가 다시 갱신 | 씀. 기록은 계속 A | 100 < 200 이라 거부. 좀비가 자기 emitter를 닫음 |
| 결과 | 디바이스가 쓸데없이 다시 연결. 기록도 계속 틀림 | 다시 연결할 일 없음. 1번과 2번 사이(최대 ping 주기)만 기록이 틀림 |

이 구멍은 좀비가 TTL(30초)보다 오래 들키지 않아야 열리므로 드물다. 하지만 RST가 오지 않는 단절에서는 수 분 동안 들키지 않으므로 "드물다"에 기댈 수 없다. epoch 방식에 드는 추가 비용(필드 하나, 비교문 하나)이 작아서 A를 고를 이유가 없다.

### epoch을 Valkey의 `TIME`으로 만들기

등록 스크립트가 Valkey의 시각으로 epoch을 만들어 서버에 돌려주는 방식. 시계가 Valkey 하나뿐이라 서버 간 시계 차이를 걱정하지 않아도 된다.

고르지 않은 이유: 서버가 Valkey의 답을 받아야만 자기 연결의 epoch을 알게 된다. 그러면 "맵에는 넣었는데 등록이 실패해서 epoch이 없는 연결"이라는 상태가 생기고, ping 때 "epoch이 없으면 등록, 있으면 갱신"으로 갈라야 한다. 시계 차이를 없애려고 관리할 상태를 하나 늘리는 교환인데, 아래 "잃는 것"에 적은 대로 시계 차이는 감수할 만한 크기다.

### 디바이스가 ping을 받을 때마다 연결 정보를 실어 응답 (backlog 0004)

디바이스가 "서버 B의 epoch 200 연결로 ping을 받았다"고 HTTP로 응답하고, 갱신은 그 응답이 왔을 때만 한다. 어느 연결이 살아 있는지 확실히 아는 쪽은 디바이스이므로 가장 정확하고, RST가 오지 않는 단절도 "N초 동안 응답 없음"으로 알아챌 수 있다. 다만 시뮬레이터, 엔드포인트, 갱신 경로가 모두 바뀐다. 이번 범위 밖.

### nginx가 디바이스 id로 서버를 정하기 (일관 해싱)

같은 id는 항상 같은 서버로 가므로 연결과 명령이 같은 서버에 도착하고, 명령을 보낼 때 `server_id`를 읽지 않아도 된다. 실무에서는 좋은 답이지만, 이 프로젝트가 다루려는 것(서버끼리 공유해야 하는 정보를 Valkey로 관리하기) 자체를 없애는 답이라 고르지 않는다. README에 검토한 방법으로 적는다.

## 결과

- 얻는 것: 좀비의 갱신이 새 연결의 기록을 덮어쓰지 못한다. 좀비를 TCP보다 먼저 닫는다. 같은 서버로 다시 연결한 경우도 Valkey에서 구분된다. 스크립트는 "쓰기"와 "삭제" 둘뿐이다.
- 잃는 것:
  - **서버끼리 시계가 맞아야 한다.** 새 연결을 받은 서버의 시계가 옛 서버보다 느리면, 새 연결의 epoch이 더 작게 찍혀 거부될 수 있다. 시계 차이가 디바이스의 재연결 간격(백오프 최소 1초)보다 작으면 문제가 없다. 시계 동기화(NTP)가 된 서버끼리는 보통 밀리초 단위로 맞는다. 차이가 더 크더라도 디바이스가 백오프 후 다시 연결하면 그동안 시간이 흘러 epoch이 커지므로, 재연결이 한두 번 더 생기고 끝난다. 이 프로젝트의 실험은 앱 두 대가 같은 호스트라 시계가 하나다.
  - 키가 만료된 상태에서 좀비가 먼저 쓰면, 진짜의 다음 갱신까지(최대 ping 주기) 기록이 틀린다. 디바이스가 다시 연결할 일은 없다.
  - 맵에 넣는 값이 emitter 하나에서 (emitter, epoch) 묶음으로 바뀐다. 묶음은 record로 만든다. record는 내용이 같으면 같은 것으로 취급하고 `SseEmitter`는 같은 객체일 때만 같으므로, `remove(id, 값)`은 지금처럼 "그 연결일 때만 제거"로 동작한다. 맵을 두 개로 나누는 방법은 두 맵이 안 맞는 순간이 생기므로 쓰지 않는다.
- 구현 메모:
  - 스크립트 파일: 쓰기는 `write_if_newest.lua`, 삭제는 `delete_if_mine.lua`. 이름에 조건이 드러나게 했다.
  - Java 쪽 `register`(연결 직후)와 `renew`(ping마다)는 뜻과 로그가 달라서 따로 두고, 둘 다 같은 쓰기 스크립트를 부른다.
  - 쓰기 스크립트 인자: ttl, 내 epoch, 그리고 필드들. 반환값 1(씀) 또는 0(거부).
  - 0을 받으면 `emitter.complete()`만 부른다. 이어서 실행되는 삭제 스크립트는 epoch이 달라 아무것도 지우지 않는다.
- 확인 결과: `experiments/2026-10-02-epoch-verification.md`. 아래 두 가지 모두 통과.
- 확인 방법 (PRD 실험 6):
  1. 시뮬레이터를 kill -9 하고 1초 안에 다시 띄운다. 조회의 `server_id`가 새 서버에서 옛 서버로 되돌아가는 순간이 없어야 한다. 옛 서버 로그에 "갱신 거부, 연결 닫음"이 찍혀야 한다.
  2. 좀비가 살아 있는 동안 키를 직접 `DEL` 한다(만료 흉내). 좀비가 먼저 쓰더라도 진짜의 다음 갱신에서 `server_id`가 돌아오고, 디바이스가 다시 연결했다는 로그가 없어야 한다.
