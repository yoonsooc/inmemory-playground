# 0003. 임대 갱신 주체를 기기에서 연결 주인 서버로 옮긴다

상태: 채택. 구현 체크리스트 1번과 2번의 원안을 대체한다. **ADR-0006으로 보완됨** (전제 "연결 주인은 진실을 안다"에 "자기 연결이 죽은 것을 즉시 안다"는 조건이 숨어 있었다)
날짜: 2026-09-29 (논의), 2026-09-30 (기록)

## 맥락

원안(CLAUDE.md 체크리스트 1번): "기기 시뮬레이터가 SSE로 연결하고 주기적으로 하트비트를 전송한다."
초기 구현(2026-09-11 `feat: device API`)은 이에 따라 `POST /devices/{id}/heartbeat`가 해시 전체(server_id 포함)를 덮어쓰고 TTL을 갱신했다.

SSE를 얹으면서 문제가 드러났다. 하트비트는 nginx 라운드로빈으로 아무 서버에나 도착한다. 기기가 app-1에 연결된 채로 하트비트가 app-2에 가면 다음 중 하나가 된다.

- `server_id`를 덮어쓰면 "app-2에 연결됨". 거짓. app-2에는 연결이 없다.
- 덮어쓰지 않으면, app-1이 이미 죽은 경우 "app-1에 연결됨". 거짓. 하트비트가 죽은 서버의 기록을 연장한다.

즉 기기가 보내는 하트비트는 이 기록을 진실로 만들 수 없다. 기기는 자기가 살아 있다는 것은 알지만 자기가 어느 서버에 붙어 있는지는 모른다.

2026-09-11 초안에서는 이 문제를 규칙 세 개로 막았다. (1) 하트비트는 server_id를 건드리지 않는다, (2) 만료된 키를 하트비트가 되살리지 않는다, (3) 해제 시 비교와 삭제를 원자적으로 한다. 규칙이 세 개나 필요하다는 것 자체가 전제가 틀렸다는 신호였다.

## 결정

- `POST /devices/{id}/heartbeat`를 없앤다. 기기는 서버에 하트비트를 보내지 않는다.
- 연결 주인 서버가 주기적 작업으로 자기 로컬 emitter 맵을 순회하며:
  1. 각 연결에 SSE `ping` 이벤트를 쓴다 (서버 → 기기 하트비트).
  2. 쓰기에 성공한 연결에 대해 `device:{id}` 해시의 TTL과 `last_seen`을 갱신한다. 기록이 없으면 다시 등록한다 (등록은 멱등).
  3. 쓰기에 실패한 연결은 맵에서 제거하고 ADR-0004의 해제 규칙을 적용한다.
- `server_id`를 쓰는 경로는 연결 주인의 등록과 갱신뿐이다.
- `last_seen`의 뜻은 "서버가 마지막으로 이 연결이 살아 있음을 확인한 시각"이다.

## 근거

- 임대 갱신의 원칙: **그 주체가 죽으면 기록이 사라져야 하는 주체**가 갱신한다. 이 기록의 뜻은 "서버 X가 이 연결을 쥐고 있다"이므로 X가 갱신해야 한다. X가 죽으면 갱신이 멈추고 TTL로 사라진다. 거짓 기록이 생기지 않는다.
- SSE의 단방향성과 맞다. 서버 → 기기 하트비트는 원래 SSE 관행이다. nginx 등 중간 장비가 유휴 연결을 끊지 못하게 하고, 쓰기 실패로 끊긴 연결을 감지한다.
- 증설이 늘리는 고장은 서버 쪽 고장(배포, 재시작, 크래시)이다. 서버 측 갱신은 바로 그 고장에서 기록이 스스로 정리되게 한다. 기기 측 하트비트는 서버 고장에 대해 아무 말도 해 주지 않는다.
- 부하: 기기 N대가 주기마다 N개의 HTTP 요청을 LB에 보내는 것보다, 서버가 자기 연결 목록을 한 번 순회하며 파이프라인으로 갱신하는 편이 가볍다.
- 초안의 규칙 (1)과 (2)가 필요 없어진다. (3)은 ADR-0004로 남는다.

## 왜 처음에 기기 측으로 설계했나

- "클라이언트가 자기 키를 TTL과 함께 쓰고 주기적으로 갱신한다"는 흔한 Redis 존재 확인 패턴을 그대로 가져왔다. 이 패턴은 기록의 뜻이 "클라이언트가 살아 있다"일 때 정확하다.
- 하트비트 API가 SSE보다 먼저 만들어졌다. 그 시점에는 기록의 뜻이 "살아 있다"였고 기기 측 갱신이 옳았다. SSE와 `server_id`가 들어오면서 기록의 뜻이 "서버 X가 쥐고 있다"로 바뀌었는데 쓰는 경로를 다시 묻지 않았다.
- 무상태 REST 서버의 습관("어느 서버가 받아도 된다")이 연결이라는 상태와 충돌했다.

## 대안

- **기기 측 하트비트 유지 + 규칙 세 개(초안)**: 동작은 하지만 경로가 둘(기기의 404 재연결, 서버의 ping 실패 정리)이라 설명이 길고, 죽은 서버의 기록을 연장하는 근본 문제가 남는다.
- **양쪽 다**: 기기 측 하트비트를 `last_seen`만 갱신하는 보조 신호로 남길 수 있다. 조용히 죽은 기기의 감지가 빨라진다. 완성 기준 밖이므로 백로그.

## 결과

- 얻는 것: 기록의 거짓이 서버 죽음 후 TTL 창 하나로 한정된다. 코드가 한 곳(주기 작업)으로 모인다.
- 잃는 것: 조용히 죽은 기기(네트워크 단절)를 늦게 감지한다. TCP 쓰기는 기기가 받았다는 확인 없이 성공으로 돌아온다. 기기 전원이 꺼지거나 네트워크가 끊겨 응답해 줄 쪽이 없으면, 서버가 다시 보내기를 포기할 때까지 몇 분이 걸릴 수 있다. 같은 컴퓨터에서 프로그램만 kill -9 한 실험은 기기 쪽 운영체제가 거절 응답(RST)을 바로 돌려주므로 현실보다 유리한 조건이다. README 한계에 적는다.
- 체크리스트 변경:

  - 2번: "해시 저장 + TTL" → "연결 주인 서버가 해시 저장과 TTL 갱신"
- 블로그 글의 서사가 이 문서다: 흔한 패턴으로 시작 → 연결이 들어오자 기록의 뜻이 바뀜 → 쓰는 주체를 옮김.
