# 0002. 서버 → 기기 채널로 SSE를 쓴다

상태: 채택
날짜: 2026-09-30

## 맥락

테이블오더 기기에는 서버가 먼저 말을 걸어야 하는 순간이 있다. 주문 상태 변화, 품절 즉시 반영, 카운터의 결제 요청, 마감 시 화면 잠금 같은 것이다. 기기 → 서버 방향(주문, 호출, 결제)은 드물고 거래 성격이다.

"SSE는 단방향인데, 어차피 연결을 쥐고 있어야 한다면 웹소켓 하나로 양방향을 처리하는 게 낫지 않은가"라는 의문이 있었다.

## 결정

- 서버 → 기기: SSE (`GET /devices/{id}/events`).
- 기기 → 서버: 일반 HTTP 요청. SSE 연결 위에 얹지 않는다.

## 근거

핵심은 연결 수가 아니라 **주문이 어느 연결을 타는가**다.

- 웹소켓으로 주문까지 보내면 주문 처리가 그 소켓을 쥔 서버에 묶인다. 요청 단위 로드밸런싱이 사라진다.
- 주문을 별도 HTTP 요청으로 보내면 아무 서버나 처리할 수 있다. 상태를 가진 표면(연결)이 푸시 방향에만 남고, 주문 경로는 무상태로 유지된다. 상태 있는 표면이 작을수록 증설과 장애 처리가 쉽다.
- HTTP 요청은 응답 코드, 타임아웃, 재시도, 멱등 키, 인증 헤더, 접근 로그, 속도 제한을 이미 갖고 있다. 웹소켓 위에서 주문을 보내면 이를 다시 만들어야 한다.
- EventSource는 자동 재연결과 마지막 이벤트 id 재개를 기본 제공한다.
- 연결 수 문제는 HTTP/1.1에 한정된다. HTTP/2에서는 SSE 스트림과 요청이 같은 TCP 연결을 다중화한다.

## 대안

필요한 조건은 하나다. 서버가 기기에게 제때 말을 걸 수 있어야 하는데, 서버는 기기에 먼저 연결할 수 없다. 매장의 기기는 공유기 뒤에 있어서 바깥에서 들어오는 연결이 막혀 있고 주소도 수시로 바뀐다. 그래서 기기가 바깥으로 연결을 열고 서버가 그 연결을 타고 말하는 방식들 중에서 고른다.

| 방법 | 연결을 여는 쪽 | 지연 | 서버가 쥐는 것 | 놓친 메시지 | 맞는 경우 |
|---|---|---|---|---|---|
| 기기가 HTTP 서버 | 서버 | 없음 | 없음 | 서버가 재시도 | 서버가 매장 안에 있을 때만 |
| 폴링 | 기기 | 묻는 주기만큼 | 없음 | 다음에 물을 때 받음 | 기기가 적고 몇 초 늦어도 될 때 |
| SSE (이 결정) | 기기 | 거의 없음 | 기기별 연결 | 따로 만들어야 함 | 서버 → 기기 알림이 주된 경우 |
| 웹소켓 | 기기 | 거의 없음 | 기기별 연결 | 따로 만들어야 함 | 양쪽이 자주 주고받을 때 |
| MQTT 브로커 | 기기 | 거의 없음 | 브로커가 대신 쥠 | 브로커가 보관 | 기기가 많고 전달을 보장해야 할 때 |
| 카프카를 기기가 직접 읽음 | 기기 | 거의 없음 | 브로커 | 보관됨 | 맞지 않음. 서버끼리 쓰는 용도 |

- **기기가 HTTP 서버가 되어 서버의 호출을 받는다.** 클라우드에 있는 서버는 기기의 주소로 요청을 보낼 방법이 없다. 매장마다 공인 주소를 주거나 포트를 열면 되지만 기기 수만큼 공격받을 문이 생기고 인증서를 기기마다 관리해야 한다. 서버가 매장 안에 있어서(매장 내 POS) 같은 공유기 아래의 기기를 부르는 구조라면 가능하다.
- **폴링.** 기기가 주기적으로 "나한테 온 것 있나"를 묻는다. 서버가 연결을 쥐지 않으므로 이 프로젝트가 다루는 문제(어느 서버가 어느 기기를 쥐고 있는지 함께 알기) 자체가 사라진다. 어느 서버가 받아도 공용 저장소를 보고 답하면 된다. 대가는 지연과 낭비다. 매장당 수십 대, 매장 수천 개가 몇 초마다 묻는 구조는 요청 대부분이 빈손이고 반응이 주기만큼 늦다. 기기가 적고 몇 초 지연이 괜찮다면 이쪽이 가장 단순한 답이다.
- **웹소켓.** 양쪽 방향 모두 잦고 지연에 민감할 때(채팅, 게임, 공동 편집) 맞다. 테이블오더의 기기 → 서버 요청은 그 조건이 아니다. 이 프로젝트의 핵심(누가 연결을 쥐고 있는지의 기록, 기록 연장, 명령 전달)은 웹소켓으로 바꿔도 그대로이므로 병행 구현은 범위에서 뺀다.
- **MQTT 브로커.** 기기가 많은 서비스에서 흔한 선택. 수많은 불안정한 기기를 상대하도록 만든 것이라, 기기별 토픽이 가볍고, 기기가 꺼져 있는 동안 온 메시지를 보관했다가 주고, 받았다는 확인을 받고, 기기가 죽으면 브로커가 알려 준다. 브로커가 모든 연결을 대신 쥐므로 "어느 서버가 어느 기기를 쥐고 있나"가 앱 서버에서 사라진다. 이 프로젝트는 앱 서버가 직접 연결을 쥐는 상황을 전제하므로, 브로커가 대신 해 주는 일을 직접 구현해 보는 셈이다.
- **카프카 토픽에 넣고 기기가 직접 읽는다.** "기기마다 우편함을 두고 기기가 꺼내 간다"는 생각은 맞지만 카프카는 그 우편함으로 맞지 않는다. 받는 쪽이 브로커 여러 대에 전용 통신 규칙으로 직접 접속해야 해서 브로커를 매장 네트워크에 노출해야 하고, 웹 화면으로 만든 기기는 쓸 수 없다. 기기마다 토픽을 만들면 토픽이 기기 수만큼 늘어나는데 그런 용도로 설계되지 않았다. 받는 쪽 목록이 바뀔 때마다 일을 다시 나누는 비용도 커서 수시로 꺼졌다 켜지는 기기와 맞지 않는다. 카프카가 맞는 자리는 서버 사이다. 주문 서비스가 "주문 상태가 바뀌었다"를 카프카에 넣고, 기기와 연결을 쥔 서버들이 그것을 읽어 기기에 내려보낸다.

실제 서비스를 설계한다면 "폴링으로 충분한가"를 먼저 묻고, 아니라면 "브로커에 맡길 것인가, 앱 서버가 직접 쥘 것인가"를 묻는 순서가 맞다. 이 프로젝트가 SSE를 고른 것은 SSE가 최선이어서가 아니라, 다루려는 문제가 "서버가 연결을 직접 쥐고 있을 때 생기는 일"이기 때문이다.

## 결과

- 얻는 것: 주문 경로가 무상태로 남는다. 인프라(프록시, 게이트웨이)를 그대로 쓴다.
- 잃는 것: 기기가 서버에 말할 수단이 SSE 연결과 분리되어 있어, 기기의 메시지는 항상 아무 서버에나 도착한다. 이 사실이 ADR-0003의 출발점이다.
- nginx 설정에 `proxy_buffering off`, `proxy_read_timeout` 연장이 필요하다. 서버가 주기적으로 무언가를 보내지 않으면 nginx 기본값 60초에 유휴 연결이 끊긴다.
