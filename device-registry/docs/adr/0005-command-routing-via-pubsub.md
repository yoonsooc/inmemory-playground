# 0005. 명령은 서버별 Pub/Sub 채널로 연결을 쥔 서버에 보낸다

상태: 채택 (구현하고 검증함, 2026-10-02)
날짜: 2026-09-30 (제안), 2026-10-02 (구현)

## 맥락

운영자의 `POST /devices/{id}/command`는 nginx를 거쳐 아무 서버에나 도착한다. 그 서버가 해당 기기의 연결을 쥐고 있지 않으면 기기에 직접 보낼 수 없다.

## 결정

1. 명령을 받은 서버는 `device:{id}` 해시에서 `server_id`를 읽는다 (`DeviceRegistryService.findOwner`).
2. 결과에 따라 세 갈래로 나뉜다 (`DeviceCommandService.command`).
   - 기록이 없다 → 기기가 오프라인이다. 보내지 않고 `OFFLINE`으로 응답한다 (404).
   - `server_id`가 나다 → 내 맵의 연결로 바로 보낸다 (`DeviceConnectionManager.commandDevice`). 보냈으면 `DELIVERED` (202). 맵에 그 연결이 없으면 `NOT_CONNECTED` (409).
   - 다른 서버다 → 그 서버만 듣는 채널 `server:{server_id}`에 발행하고 `PUBLISHED`로 응답한다 (202).
3. 각 서버는 기동할 때 자기 채널 `server:{내 server_id}` 하나만 구독한다 (`CommandSubscriberConfig`).
4. 채널에서 메시지를 받은 서버는 자기 맵에서 연결을 찾아 SSE `command` 이벤트로 보낸다. 맵에 없으면 경고 로그를 남기고 버린다 (`DeviceCommandService.onPublished`).

메시지는 JSON 문자열 `{"deviceId": "...", "payload": "..."}`이다. 채널이 서버 단위라서 어느 기기 것인지를 메시지 안에 담는다. 명령 본문은 받은 그대로 문자열로 넘긴다.

## 근거

- 채널을 서버별로 두면 명령이 모든 서버에 뿌려지지 않는다. 기록에서 연결을 쥔 서버를 찾아 그 서버에게만 보낸다. Valkey의 기록(ADR-0001)이 있어야 가능한 방식이다.
- 4번의 경고 로그가 "기록과 실제 연결이 어긋난 순간"을 드러낸다. ADR-0006 덕분에 이 로그는 서버가 죽거나 재시작한 뒤 TTL이 남은 동안에만 나와야 한다.
- 명령을 판단하고 보내는 로직은 별도 클래스에 두었다. `DeviceConnectionManager`가 이미 `DeviceRegistryService`를 쓰고 있어서, 서비스 쪽에 넣으면 둘이 서로를 참조하게 된다.

## 감수한 것

- **전달을 보장하지 않는다.** Pub/Sub는 구독자가 없으면 메시지를 버린다. 응답의 `PUBLISHED`는 "발행했다"는 뜻이고 "기기가 받았다"는 뜻이 아니다. 받았는지 확인하는 기능은 백로그 0007.
- **서버가 죽은 직후 TTL(최대 30초) 동안 온 명령은 사라진다.** 죽은 서버의 기록이 남아 있어 그 서버의 채널로 발행되는데, 듣는 서버가 없다. 실험에서 죽은 지 1초 뒤의 명령이 202 `PUBLISHED`를 받고 아무 데도 도착하지 않았다.
- **기록을 읽은 직후 기기가 서버를 옮기면 그 명령은 사라진다.** 받은 서버가 기록에서 읽은 서버의 채널로 발행하는데, 그 사이 기기가 다른 서버에 다시 붙었다면 옛 서버는 맵에 연결이 없어 버린다. 실험에서 읽기부터 전달까지 약 20ms였다. 옛 서버에 경고 로그("published here but no local connection")가 남는다. 줄이는 방법은 백로그 0009.
- **중요한 상태를 이 경로 하나에 맡기면 안 된다.** 어느 방식을 쓰든 Pub/Sub는 놓친 메시지를 다시 주지 않는다. 주문 같은 기기 → 서버 요청은 이 경로를 타지 않고 일반 HTTP 요청과 응답으로 처리한다. 서버 → 기기 알림이 사라져도 되게 하려면, 기기가 재연결할 때 현재 상태를 다시 받아 오게 한다.
- **발행 명령이 돌려주는 "받은 구독자 수"를 쓰지 않는다.** 클러스터에서는 발행을 받은 노드에 붙은 구독자만 세므로, 실제로 전달됐어도 0이 나올 수 있다. 그래서 "0이면 실패"로 응답하지 않는다.
- 클러스터에서 Pub/Sub 메시지는 모든 노드로 퍼진다. 규모가 크면 슬롯 단위로 퍼지는 Sharded Pub/Sub(`SPUBLISH`)를 검토한다. 이 프로젝트 규모에서는 문제되지 않는다.

## 검토하고 고르지 않은 방법

### 모든 서버에 뿌리고 각자 거르기

모든 서버가 같은 채널(전체 하나, 또는 매장별)을 구독한다. 명령을 받은 서버는 기록을 읽지 않고 그 채널에 발행만 한다. 메시지를 받은 서버들은 각자 자기 맵을 보고, 그 기기의 연결을 쥐고 있으면 보내고 없으면 버린다. Socket.IO의 Redis 어댑터가 이렇게 동작하고, 채팅 서버에서 흔히 쓰인다.

| | 모두에게 뿌리고 각자 거르기 | 기록을 보고 한 서버에만 보내기 (이 결정) |
|---|---|---|
| 메시지 하나가 닿는 서버 | 전부 | 한 대 |
| 서버가 늘 때 | 메시지 수 × 서버 수만큼 받고 버리는 일이 늘어남 | 그대로 |
| 보내는 쪽이 아는 것 | 아무것도 모름. 항상 "보냈다" | 오프라인(404)인지, 기록이 어긋났는지(409) 바로 앎 |
| 기록이 틀렸을 때 | 영향 없음 | 그 사이 명령이 사라짐 (최대 TTL) |
| 기록을 읽은 직후 기기가 다른 서버로 옮겼을 때 | 새 서버도 메시지를 받으므로 전달됨 | 옛 서버의 채널로 가서 사라짐 (읽기부터 전달까지 약 20ms의 창) |
| 기기가 끊기고 아직 다시 붙지 못한 사이 | 사라짐. 어느 서버의 맵에도 없음 | 사라짐 |
| 매장 전체에 알리기 (품절 반영 등) | 발행 한 번 | 기기마다 기록을 읽고 따로 보냄 |
| 누가 온라인인지 조회 | 못 함. 기록이 따로 필요 | 됨 |

고르지 않은 이유:

- 이 프로젝트가 다루려는 것이 "어느 서버가 어느 기기를 쥐고 있는지를 서버끼리 함께 아는 것"이다. 그 기록은 상태 조회(체크리스트 3번) 때문에 어차피 필요하고, 이미 있는 기록으로 보낼 서버를 정하면 메시지가 한 대에만 간다.
- 보내는 쪽이 결과를 알 수 있다. 뿌리는 방식에서는 기기가 오프라인이어도 보낸 쪽은 알 수 없다.
- 기록이 틀리는 경우는 ADR-0006으로 줄였다. 기기가 다른 서버로 옮기면 그 순간 기록이 바뀐다. 그래도 두 가지 경우가 남는다. 하나는 기기가 끊기고 아직 재연결하지 못한 사이인데, 이때의 명령은 뿌리는 방식에서도 똑같이 사라진다. 다른 하나는 기록을 읽은 직후에 기기가 서버를 옮긴 경우인데, 이때는 뿌리는 방식이 낫다. 이 창은 읽기부터 전달까지 약 20ms이고, 받은 서버가 한 번 다시 넘기게 하면 줄일 수 있다 (백로그 0009).

반대로 골랐을 조건:

- 서버가 몇 대 안 되고 메시지가 많지 않다. 받고 버리는 비용이 문제되지 않고, 기록을 읽는 단계가 없는 만큼 단순하다.
- 기기 하나가 아니라 매장 전체에 알리는 일이 대부분이다. 이때는 매장별 채널이 자연스럽다. 다만 모든 서버가 모든 매장 채널을 듣게 하면 채널을 나눈 효과가 없으므로, 서버가 그 매장의 기기를 쥐고 있을 때만 그 채널을 구독하게 한다.

실제 서비스에서는 둘을 같이 쓰는 경우가 많다. 상태 조회용 기록은 두고, 전달은 뿌리거나 좁혀 보내거나 중에서 메시지 종류에 맞게 고른다.

### 서버끼리 직접 호출

기록에서 서버를 찾은 뒤 그 서버의 내부 주소로 HTTP 요청을 보내는 방식. 서버가 서로의 주소를 알아야 하고 서버 간 호출의 실패 처리가 따로 필요하다. 채널에 발행하는 방식은 서버가 서로의 주소를 모른 채 Valkey만 거친다.
