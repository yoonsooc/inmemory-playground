# 0005. 명령은 서버별 Pub/Sub 채널로 연결을 쥔 서버에 보낸다

상태: 채택 (구현·검증됨, 2026-10-02)
날짜: 2026-09-30 (제안), 2026-10-02 (구현)

## 맥락

운영자의 `POST /devices/{id}/command`는 nginx를 거쳐 아무 서버에나 도착한다. 그 서버가 해당 기기의 연결을 쥐고 있지 않으면 기기에 직접 보낼 수 없다.

## 결정

1. 명령을 받은 서버는 `device:{id}` 해시에서 `server_id`를 읽는다 (`DeviceRegistryService.findOwner`).
2. 결과에 따라 세 갈래로 나뉜다 (`DeviceCommandService.command`).
   - 기록이 없다 → 기기가 오프라인이다. 보내지 않고 `OFFLINE`으로 응답한다 (404).
   - `server_id`가 나다 → 내 맵의 연결로 바로 보낸다 (`DeviceConnectionManager.commandDevice`). 보냈으면 `DELIVERED` (202). 맵에 그 연결이 없으면 `NOT_CONNECTED` (409).
   - 다른 서버다 → 그 서버만 듣는 채널 `server:{server_id}`에 발행하고 `PUBLISHED`로 응답한다 (202).
3. 각 서버는 기동할 때 자기 채널 `server:{내 server_id}` 하나만 구독한다 (`CommandSubscriberConfig`).
4. 채널에서 메시지를 받은 서버는 자기 맵에서 연결을 찾아 SSE `command` 이벤트로 보낸다. 맵에 없으면 경고 로그를 남기고 버린다 (`DeviceCommandService.onPublished`).

메시지는 JSON 문자열 `{"deviceId": "...", "payload": "..."}`이다. 채널이 서버 단위라서 어느 기기 것인지를 메시지 안에 담는다. 명령 본문은 받은 그대로 문자열로 넘긴다.

## 근거

- 채널을 서버별로 두면 명령이 모든 서버에 뿌려지지 않는다. 기록에서 연결을 쥔 서버를 찾아 그 서버에게만 보낸다. Valkey의 기록(ADR-0001)이 있어야 가능한 방식이다.
- 4번의 경고 로그가 "기록과 실제 연결이 어긋난 순간"을 드러낸다. ADR-0006 덕분에 이 로그는 서버가 죽거나 재시작한 뒤 TTL이 남은 동안에만 나와야 한다.
- 명령을 판단하고 보내는 로직은 별도 클래스에 두었다. `DeviceConnectionManager`가 이미 `DeviceRegistryService`를 쓰고 있어서, 서비스 쪽에 넣으면 둘이 서로를 참조하게 된다.

## 감수한 것

- **전달을 보장하지 않는다.** Pub/Sub는 구독자가 없으면 메시지를 버린다. 응답의 `PUBLISHED`는 "발행했다"는 뜻이고 "기기가 받았다"는 뜻이 아니다. 받았는지 확인하는 기능은 백로그 0007.
- **서버가 죽은 직후 TTL(최대 30초) 동안 온 명령은 사라진다.** 죽은 서버의 기록이 남아 있어 그 서버의 채널로 발행되는데, 듣는 서버가 없다. 실험에서 죽은 지 1초 뒤의 명령이 202 `PUBLISHED`를 받고 아무 데도 도착하지 않았다.
- **발행 명령이 돌려주는 "받은 구독자 수"를 쓰지 않는다.** 클러스터에서는 발행을 받은 노드에 붙은 구독자만 세므로, 실제로 전달됐어도 0이 나올 수 있다. 그래서 "0이면 실패"로 응답하지 않는다.
- 클러스터에서 Pub/Sub 메시지는 모든 노드로 퍼진다. 규모가 크면 슬롯 단위로 퍼지는 Sharded Pub/Sub(`SPUBLISH`)를 검토한다. 이 프로젝트 규모에서는 문제되지 않는다.
