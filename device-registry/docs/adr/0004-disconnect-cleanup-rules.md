# 0004. 연결 해제 시 자기 기록만 원자적으로 지운다

상태: 채택. **삭제 조건은 ADR-0006으로 변경됨** (`server_id` 비교 → epoch 일치)
날짜: 2026-09-11 (초안 실험에서 확인), 2026-09-30 (기록)

## 맥락

서버 A가 기기 dev-1의 연결 끊김을 알아채는 데는 시간이 걸린다(ping 주기, TCP 오류 보고). 기기는 자기 쪽에서 끊김을 즉시 알고 바로 재연결하므로, A의 해제 콜백이 실행되는 시점에는 dev-1이 이미 서버 B에 재연결해 `server_id=B`가 기록되어 있는 경우가 보통이다.

```
경우 1  B 등록 ───────────────▶ A 콜백(읽기: B, 삭제 안 함)        정상
경우 2  A 콜백(읽기: A, 삭제) ──▶ B 등록                            정상. 기록이 잠깐 없다가 B가 새로 씀
경우 3  A 콜백 읽기(A) ──▶ B 등록 ──▶ A 콜백 삭제                   사고. B의 기록이 지워짐
```

또 재연결이 라운드로빈으로 **다시 A에** 착지하면, 새 연결도 `server_id=A`라서 `server_id` 비교로는 옛 연결의 콜백과 새 연결을 구분할 수 없다.

## 결정

1. 해제 콜백은 `device:{id}`의 `server_id`가 자기 자신일 때만 해시를 지운다.
2. 비교와 삭제는 원자적으로 한다 (Lua 스크립트 한 번 실행). 경우 3을 없앤다.
3. 같은 서버 재연결은 서버 로컬에서 구분한다. 로컬 맵에서 "이 기기 id에 매핑된 값이 정확히 이 콜백의 emitter 인스턴스일 때만 제거"하고, 제거에 성공한 경우에만 1번을 실행한다. 새 연결이 들어와 있으면 옛 콜백은 아무것도 하지 않는다.
4. 기록이 없는데 연결이 살아 있으면(예: 서버가 잠시 Valkey에 못 썼다가 복구) 연결을 끊지 않고 기록을 다시 쓴다. 믿어야 할 것은 실제 연결이고, Valkey의 기록은 그것을 알리려고 적어 둔 메모다. 메모가 사라졌다고 멀쩡한 연결을 끊지 않는다.

## 근거

- 실제 연결과 Valkey 기록 중 실제 연결을 믿는다(ADR-0001). 연결이 살아 있는 한 기록은 언제든 다시 적을 수 있다. 반대로 기록을 잘못 지우면 살아 있는 연결이 라우팅에서 사라진다.
- 비교와 삭제 사이의 간격은 락 실무 질문의 핵심이다. "토큰 소유 확인 후 해제"를 원자적으로 해야 하는 분산 락과 같은 구조다.
- 같은 서버 재연결 구분을 로컬 맵의 인스턴스 동일성으로 처리하면 저장소 스키마를 바꾸지 않아도 된다.

## 대안

- **해제 시 아무것도 지우지 않고 TTL에 맡김**: 단순하지만 정상 종료에도 TTL만큼 ONLINE으로 남는다. 초안 실험에서 ping 실패 감지 13초 뒤 즉시 OFFLINE이 된 것과 비교해 사용자가 보는 정합성이 나쁘다.
- **WATCH/MULTI/EXEC**: 가능하지만 클러스터에서 키 하나에 대한 Lua가 더 짧고 읽기 쉽다.
- **연결마다 토큰을 만들어 해시에 저장하고 토큰까지 비교**: 같은 서버 재연결을 저장소 수준에서 구분한다. 서버 재시작 후 옛 토큰이 남는 경우 등에 더 견고하지만, 완성 기준 밖이므로 백로그.

## 결과

- 얻는 것: 정상 종료와 감지된 끊김은 즉시 OFFLINE. 재연결 경합에서 살아 있는 기록이 지워지지 않는다.
- 잃는 것: Lua 스크립트 하나와 그 테스트가 필요하다.
- 확인 방법: 실험 3(기기 kill -9)과 실험 2(서버 kill 후 재연결이 다른 서버에 착지)에서 로그로 본다.
